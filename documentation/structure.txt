# SHS Distributed GPU Inference System - Worker Node File Structure

## 1. 목적

이 문서는 SHS Distributed GPU Inference System의 **Worker Node** 파일 구조와 각 파일의 역할을 정리한다.

Worker Node는 실제 GPU 연산을 수행하는 실행 서버이며, 중앙 서버가 없어도 단독으로 실행·테스트할 수 있어야 한다.

현재 Worker Node는 다음 방향으로 구현되었다.

- FastAPI 기반 Worker Node
- Executor 기반 AI 작업 실행
- Priority Queue 기반 Task 처리
- Whisper 음성 인식
- Ollama LLM text generation
- Central Server용 Generic Worker Task API
- JSON / multipart 작업 제출 지원
- Capability Manifest 제공
- Central Server register / heartbeat client 구조
- 작업 결과 파일 목록 조회 API
- 작업 결과 파일 다운로드 API
- path 기반 artifact 다운로드 API
- Central Server가 Worker artifact를 proxy할 수 있는 구조

---

## 2. Worker Node의 역할

Worker Node는 다음 역할을 가진다.

1. 시스템 및 GPU 상태 수집
2. 지원 가능한 AI 작업 목록 제공
3. 로컬 작업 실행 API 제공
4. 중앙 서버용 Generic Worker API 제공
5. executor 기반 추론 수행
6. 작업을 priority queue로 관리
7. 작업 결과 파일 저장
8. 작업 상태 조회 제공
9. 결과 파일 목록 조회 제공
10. 결과 파일 다운로드 제공
11. path 기반 artifact 다운로드 제공
12. 중앙 서버에 register / heartbeat 전송
13. 중앙 서버 없이 단독 실행 가능

---

## 3. 설계 원칙

### 3.1 노드는 독립 실행 가능해야 한다

중앙 서버가 없어도 Worker Node 자체 API와 Swagger UI로 작업을 실행할 수 있어야 한다.

대표 로컬 테스트 API:

```text
POST /api/local/tasks/llm/generate
POST /api/local/tasks/whisper
GET  /api/local/tasks
GET  /api/local/tasks/{task_id}
GET  /api/local/queue
3.2 실제 추론 로직은 executor에 둔다

FastAPI 라우터에는 모델 실행 코드를 직접 작성하지 않는다.

실제 실행 로직은 다음 위치에 둔다.

app/executors/

예:

app/executors/whisper_executor.py
app/executors/llm_ollama_executor.py
3.3 새로운 기능 추가는 executor 추가 중심으로 한다

새로운 모델이나 기능을 추가할 때는 가능하면 다음 작업만 수행한다.

executor 파일 추가
BaseExecutor 상속
task_type 지정
run(payload, work_dir) 구현
get_input_schema() 구현
get_output_schema() 구현
get_required_resources() 구현
registry에 등록

Central Server는 Worker의 /api/capabilities를 보고 새로운 executor를 인식해야 한다.

3.4 중앙 서버 통신과 로컬 실행은 분리한다

로컬 테스트 API와 중앙 서버용 API는 분리한다.

/api/local/*
로컬 개발/테스트/디버깅용
인증 없이 사용 가능
Swagger UI에서 직접 테스트 가능
/api/worker/*
Central Server 전용
SHS_INTERNAL_API_KEY 기반 인증 필요
JSON/multipart generic task submit 지원
artifact 다운로드 지원
3.5 Central Server는 task_type별 API를 몰라도 된다

Central Server는 다음처럼 task별 API를 직접 호출하지 않는다.

POST /api/local/tasks/llm/generate
POST /api/local/tasks/whisper

대신 항상 다음 generic API를 사용한다.

POST /api/worker/tasks

파일이 없는 작업은 JSON으로, 파일이 필요한 작업은 multipart로 보낸다.

3.6 외부 클라이언트는 Worker Node를 직접 호출하지 않는다

SHSAITools 같은 외부 클라이언트는 Worker Node 주소를 알 필요가 없다.

올바른 artifact 다운로드 흐름은 다음과 같다.

SHSAITools
→ Central Server
→ Worker Node
→ Worker task work_dir/output 파일

SHSAITools는 Central Server만 호출한다.

GET /api/tasks/{central_task_id}/artifacts?path=output/result.txt

Central Server는 내부적으로 Worker Node를 호출한다.

GET /api/worker/tasks/{worker_task_id}/artifacts?path=output/result.txt

app/api/worker_tasks.py

Central Server 전용 Generic Worker Task API이다.

현재 가장 중요한 중앙 서버 연동 API이다.

모든 /api/worker/* 요청은 internal API key 인증을 요구한다.

필수 헤더:

x-shs-internal-api-key: change-this-secret

현재 엔드포인트:

POST  /api/worker/tasks
GET   /api/worker/tasks/{task_id}
GET   /api/worker/tasks/{task_id}/files

POST  /api/worker/tasks/{task_id}/cancel
PATCH /api/worker/tasks/{task_id}/priority
POST /api/worker/tasks

Central Server가 Worker Node에 작업을 제출하는 generic endpoint이다.

지원 Content-Type:

application/json
multipart/form-data

JSON 작업 예:

{
  "task_type": "llm_generate",
  "priority": 5,
  "payload": {
    "model": "llama3.2:latest",
    "prompt": "hello",
    "format": "text",
    "keep_alive": "5m"
  },
  "metadata": {
    "central_task_id": "central_task_001",
    "requested_by": "admin"
  }
}

Multipart 작업 예:

metadata_json:
{
  "task_type": "whisper",
  "priority": 5,
  "payload": {
    "model": "base",
    "language": "auto",
    "output_format": "all",
    "file_inputs": {
      "input_file": "uploaded_audio"
    }
  },
  "metadata": {
    "central_task_id": "central_task_whisper_001",
    "requested_by": "admin"
  }
}

uploaded_audio:
sample.mp3

중요:

multipart 파일 매핑은 file_inputs로 통일한다.
file_map은 사용하지 않는다.

의미:

"file_inputs": {
  "input_file": "uploaded_audio"
}

form field uploaded_audio에 담긴 파일을 저장한 뒤, executor payload의 input_file에 저장 경로를 넣는다.

GET /api/worker/tasks/{task_id}

Central Server가 Worker Task 상태를 polling할 때 사용한다.

응답에는 다음이 포함된다.

task status
result
error_message
output_files
central_task_id
requested_by
source
metadata

Worker가 재시작되면 기존 task_id가 메모리에서 사라질 수 있다.

따라서 이 API는 404를 반환할 수 있다.

Central Server는 이 경우 다음 중 하나로 처리한다.

worker_task_lost
failed
unknown
retry_pending
GET /api/worker/tasks/{task_id}/files

Task output 디렉토리의 파일 목록을 반환한다.

예:

{
  "ok": true,
  "task_id": "worker_task_id",
  "files": [
    {
      "name": "result.json",
      "path": "output/result.json",
      "size_bytes": 1024,
      "content_type": "application/json"
    }
  ]
}

현재 구현 기준:

data/tasks/{task_id}/output/ 아래 파일을 조회한다.
output 하위 파일을 재귀적으로 조회할 수 있다.
반환되는 path는 artifact 다운로드 API에 그대로 사용할 수 있다.

예:

output/result.txt
output/result.json
output/result.srt
output/nested/archive.zip
GET /api/worker/tasks/{task_id}/files/{filename}

기존 호환용 Task output 파일 다운로드 API이다.

보안 규칙:

filename은 순수 파일명만 허용
../ path traversal 금지
data/tasks/{task_id}/output 바로 아래 파일만 허용

예:

GET /api/worker/tasks/{task_id}/files/result.txt

주의:

새로운 Central Server artifact proxy에는 가능하면 아래 path 기반 API를 사용한다.

GET /api/worker/tasks/{task_id}/artifacts?path=output/result.txt
GET /api/worker/tasks/{task_id}/artifacts?path={artifact_path}

Central Server 전용 path 기반 Worker Artifact Download API이다.

이 API는 이번 artifact download 개선에서 추가된 핵심 endpoint이다.

예:

GET /api/worker/tasks/abc-123/artifacts?path=output/result.txt
GET /api/worker/tasks/abc-123/artifacts?path=output/result.json
GET /api/worker/tasks/abc-123/artifacts?path=output/result.srt
GET /api/worker/tasks/abc-123/artifacts?path=output/audio.wav
GET /api/worker/tasks/abc-123/artifacts?path=output/video.mp4
GET /api/worker/tasks/abc-123/artifacts?path=output/nested/archive.zip

주의:

이 API는 SHSAITools가 직접 호출하지 않는다.

SHSAITools는 Central Server를 호출한다.

GET /api/tasks/{central_task_id}/artifacts?path=output/result.txt

Central Server가 내부적으로 Worker를 호출한다.

GET /api/worker/tasks/{worker_task_id}/artifacts?path=output/result.txt

동작:

worker_task_id로 Worker task 조회
path query parameter 검증
task work_dir 기준 상대 경로로 해석
output/ 하위 파일인지 확인
최종 resolve 경로가 task work_dir 내부인지 확인
파일 존재 확인
FileResponse로 stream 반환

허용되는 path 예:

output/result.txt
output/result.json
output/result.srt
output/audio.wav
output/video.mp4
output/image.png
output/archive.zip
output/nested/archive.zip

거부되는 path 예:

../secret
../../.env
/etc/passwd
output/../../secret
C:\Windows\System32\config
C:/Windows/System32/config
\\server\share\file.txt
//server/share/file.txt
result.txt

result.txt만 넣으면 안 된다.

반드시 output/result.txt처럼 output/부터 시작해야 한다.

응답:

파일이 있으면 200 OK
파일은 stream으로 반환
Content-Disposition은 attachment filename 기반으로 설정
Content-Type은 확장자 기반으로 추정
알 수 없는 확장자는 application/octet-stream

Content-Type 예:

result.txt  -> text/plain
result.json -> application/json
result.srt  -> application/x-subrip
audio.wav   -> audio/wav
video.mp4   -> video/mp4
unknown.bin -> application/octet-stream

에러:

Unknown worker_task_id -> 404
Missing path           -> 422 또는 400
Invalid path           -> 400
File not found         -> 404
Invalid internal key   -> 401 또는 403
POST /api/worker/tasks/{task_id}/cancel

queued 또는 pending 작업을 취소한다.

현재 MVP 규칙:

pending: 취소 가능
queued: 취소 가능
running: 취소 불가
completed: 취소 불가
failed: 취소 불가
cancelled: 취소 불가
PATCH /api/worker/tasks/{task_id}/priority

queued 상태 작업의 priority를 변경한다.

요청:

{
  "priority": 20
}

규칙:

queued 상태만 변경 가능
running/completed/failed/cancelled는 변경 불가

16. Central Server 개발 시 Worker Task 처리 전제
16.1 POST 응답은 결과가 아니다
POST /api/worker/tasks

응답은 작업 결과가 아니라 queue 등록 결과이다.

정상 예:

{
  "ok": true,
  "task": {
    "id": "worker_task_id",
    "status": "queued",
    "result": null
  }
}

Central Server는 worker_task_id를 저장하고 polling해야 한다.

16.2 Worker Task는 메모리 기반이다

현재 Worker Task 정보는 메모리 기반이다.

Worker가 재시작되면 기존 task_id가 사라질 수 있다.

따라서:

GET /api/worker/tasks/{task_id}

는 404를 반환할 수 있다.

Central Server는 이를 전제로 처리해야 한다.

16.3 Central Task ID와 Worker Task ID는 분리한다

Central Server는 자체 task id를 갖는다.

Worker Node는 자체 task id를 갖는다.

Central Server는 매핑을 저장해야 한다.

central_task_id ↔ worker_task_id

Worker 요청 metadata에 central_task_id를 넣는 것을 권장한다.

{
  "metadata": {
    "central_task_id": "central_task_001",
    "requested_by": "admin"
  }
}
16.4 Artifact 다운로드 시에도 ID를 구분해야 한다

SHSAITools가 아는 task_id는 Central Server의 task_id이다.

central_task_id

Worker Node가 아는 task_id는 Worker 내부 task_id이다.

worker_task_id

따라서 외부 클라이언트 호출:

GET /api/tasks/{central_task_id}/artifacts?path=output/result.txt

Central Server 내부 호출:

GET {worker.base_url}/api/worker/tasks/{worker_task_id}/artifacts?path=output/result.txt

Central Server는 반드시 다음 매핑을 저장해야 한다.

central_task_id
worker_task_id
selected_node_id
worker_base_url

GET {worker.base_url}/api/worker/tasks/{worker_task_id}/artifacts?path=output/result.txt

Content-Disposition
Content-Length

현재 Worker Node는 Central Server MVP와 연동 가능한 수준이지만, 다음은 향후 개선 사항이다.
